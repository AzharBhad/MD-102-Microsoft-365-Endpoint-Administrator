# 1.3.8 Manage the membership of local groups on Windows devices by using Intune

> **Exam objective:** Manage the membership of local groups on Windows devices by using Intune
>
> **Domain:** 1 - Prepare infrastructure for devices (20-25%) · **Skill:** 1.3 Implement identity and compliance
>
> **Hands-on:** [LAB-1.13 Windows LAPS and local group membership](../labs/LAB-1.13-windows-laps-local-groups.md)

## Concept in plain English

Group Policy *Restricted Groups* doesn't exist for Entra joined devices. Intune replaces it with the **Local user group membership** policy under **Endpoint security > Account protection**. It uses the **LocalUsersAndGroups** CSP to add, remove or replace members of built-in local groups such as *Administrators* or *Remote Desktop Users*.

Other ways to control local admins (know when to use which):

| Mechanism | Scope | Notes |
|---|---|---|
| **Intune Local user group membership** (Account protection) | Device groups you target | Granular, per-group, supports **Replace** |
| Entra **Microsoft Entra Joined Device Local Administrator** role | **All** Entra joined devices | Tenant-wide - no per-device scoping |
| Entra device setting *Registering user is added as local administrator* | The user who joins the device | Set to None/Selected for least privilege |
| **Windows Autopilot profile** *User account type = Standard* | Autopilot user | Prevents the primary user becoming admin |
| Settings catalog *Local Users And Groups* | Same CSP | Equivalent to the Account protection template |
| Custom OMA-URI `./Device/Vendor/MSFT/Policy/Config/LocalUsersAndGroups/Configure` | Same CSP | XML payload, legacy approach |

## How it works

```mermaid
flowchart LR
  P["Account protection policy<br/>Local user group membership"] --> C["LocalUsersAndGroups CSP<br/>(Windows 10 20H2+)"]
  C --> A{Action}
  A -->|Add (Update)| U[Add listed members,<br/>keep existing]
  A -->|Remove (Update)| R[Remove listed members,<br/>keep others]
  A -->|Add (Replace)| X["Replace ALL members<br/>with the listed ones<br/>(built-in Administrator is kept)"]
```

Members can be **Entra users/groups** (resolved to SIDs; Entra groups work on Entra joined devices), **AD users/groups** (hybrid, as `DOMAIN\name` or SID), or **local accounts**.

## Licensing requirements

Intune Plan 1. Windows 10 20H2 or later / Windows 11. Entra joined or hybrid joined.

## Configuration steps

1. **Endpoint security > Account protection > Create policy** → Platform **Windows** → Profile **Local user group membership**.
2. **Configuration settings > Local group membership > Add**:

| Field | Example |
|---|---|
| Local group | **Administrators** (others: Users, Guests, Power Users, Remote Desktop Users, Remote Management Users) |
| Group and user action | **Add (Update)** / Remove (Update) / **Add (Replace)** |
| User selection type | **Users/Groups** (pick from Entra) or **Manual** (enter SID or `DOMAIN\user`) |
| Selected users | `SG-Lab-Helpdesk` |

3. Add a second row if needed, for example *Remote Desktop Users → Add (Update) → SG-Lab-Helpdesk*.
4. Assign to a **device group**, for example `DG-Lab-Windows-Corporate`.

### Verify on the device

```powershell
Get-LocalGroupMember -Group 'Administrators'
# Entra groups appear as their SID (S-1-12-1-...) because Windows resolves them at sign-in token time
```

MDM diagnostic report: **Settings > Accounts > Access work or school > Export your management log files** → look for `LocalUsersAndGroups`.

## Comparison: Update vs Replace

| Action | Existing members | Listed members | Risk |
|---|---|---|---|
| Add (Update) | Kept | Added | Low |
| Remove (Update) | Kept (except listed) | Removed | Low |
| **Add (Replace)** | **Removed** (except built-in Administrator) | Become the only members | **High** - can remove Entra roles SIDs and the primary user; test in a pilot first |

## Exam tips and common traps

- **"Help desk group must be local admin only on devices in the London office"** → **Local user group membership** policy assigned to the London **device group** (the Entra *Joined Device Local Administrator* role is tenant-wide and can't be scoped).
- **"Remove all unapproved accounts from the local Administrators group"** → **Add (Replace)**.
- The policy is **device-targeted**. User group assignments aren't the intended scope.
- Conflicts: two policies with **Replace** on the same group = conflict. Mixing Replace with Update produces unpredictable results - avoid it.
- Entra group membership changes take effect at the next **sign-in** because group SIDs are evaluated in the user's token.

## Real-world notes

- A common enterprise pattern: **Replace** Administrators with *\[built-in Administrator (LAPS-managed)] + SG-Workstation-Admins (PIM-eligible)*. Users run as standard and use EPM for approved elevations.
- Document every Replace policy. It silently removes the Entra *Global Administrator* and *Joined Device Local Administrator* role SIDs added at join time, which surprises admins.
